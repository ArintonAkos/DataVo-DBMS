2. First reading (superseded by section 3):
- Both builds have two speeds for this query: about 2.1 ms and about 11-14 ms. The slow speed is the
  ~14 ms p99 of every normal run on both builds.
- With loops fully optimized from the start, the slow speed disappears (p99 about 4 ms). The slow
  speed is therefore the exact-scan loop running as tier-0 / on-stack-replacement code before tiered
  compilation replaces it, not the algorithm. When the replacement is late, a whole run's median
  lands in the slow mode.
- HEAD fell into the slow mode for the whole run in 3 of 14 runs (official run included), master in
  0 of 11. That difference is suggestive but not statistically established with these counts
  (Fisher's exact test, two-sided, p about 0.23). Commit a8b3bca changed FlatVectorIndex's scan
  (pooled NearestHeap), which may change when the loop is promoted.
- Not done here: an engine change (for example AggressiveOptimization on the scan kernel) and a re-run.
  It is recorded as a follow-up; the official numbers are left as measured.

3. Cause and fix (2026-11-17, after the above)

Marking FlatVectorIndex.SearchIntoTopK alone with AggressiveOptimization did NOT fix it: 15 runs gave
  2.10 2.06 2.17 2.21 12.68 2.26 12.33 12.81 2.12 2.11 2.13 2.11 2.12 2.26 2.16 ms (p50), p99 12.8-17.3 ms.

JIT compile logs (DOTNET_JitStdOutFile + DOTNET_JitDisasmSummary=1) of a slow run (12.84 ms) and a fast run
(2.13 ms) show the same final code in both: SearchIntoTopK FullOpts; SimdDistanceKernels.Dot and its workers
TryDotAvx / TryDotAdvSimd (separate methods, not inlined) go Tier0 -> Instrumented Tier0 -> Tier1. What
differs is when: Dot reached Tier1 at compile event 3,938 in the slow run and 3,519 in the fast one.
Tiered compilation promotes a method only after a quiet period in JIT activity; every search before that
computed 50,000 distances with tier-0 Vector128 code (~12 ms). Late promotion puts the run's median in the
slow mode; the first few timed searches of every run were the ~14 ms p99. DOTNET_TC_QuickJitForLoops=0
compiles methods with loops (the SIMD workers) fully optimized at once, which is why it removed both.

Fix, commit 5cbcd14: SimdDistanceKernels.Dot / CosineDistance / EuclideanDistance (span entry points) are
AggressiveOptimization and their per-ISA workers (AVX, AVX-512, AdvSimd, portable) AggressiveInlining;
SearchIntoTopK keeps AggressiveOptimization. Compile log after the fix: Dot compiled once, FullOpts, workers
inlined (no TryDot* entries), no tier-0 or instrumented versions. Disassembly of SearchIntoTopK (FullOpts):
GetVectorReadOnlySpan, CosineDistanceFromDot and IsBetter inlined; out-of-line calls only to the distance
kernels and InsertSorted. (An intermediate variant with AggressiveOptimization on every worker, not
inlined, measured the same: 2.21-2.28 ms.)
