\title{DataVo DBMS and the SVM Storage Model: Managed Runtime Database Engines Beyond Object-Oriented Hot Paths}

\author{DataVo Benchmark Research Report\\
\small Expanded technical whitepaper derived from \texttt{whitepaper\_benchmark\_rerun\_2026-07-03-v2.txt}\\
\small Apple Silicon macOS benchmark environment}
\date{}

\begin{abstract}
Managed database engines have historically been constrained by allocation pressure, object graph traversal, reflective type mapping, primitive boxing, and garbage-collector interference in latency-sensitive hot paths. This paper analyzes DataVo DBMS as an example of a managed C\# storage engine that breaks through that ceiling when the execution path bypasses object-oriented convenience layers and instead treats relational data as explicit byte-layout arrays. We introduce the Storage Virtualization Model (SVM), DataVo's byte-addressed storage contract boundary between logical relational semantics and physical row layout. SVM does not expose objects to the storage layer; it exposes row ids, schemas, and encoded bytes. That boundary lets the engine compile eligible operations into typed readers, fixed-width patches, and zero-allocation fast paths without changing relational semantics. After production hardening, DataVo's LSM path integrates a binary WAL, atomic SSTable and manifest publication, ARM64 memory-ordering barriers, and MVCC snapshot-retention safety. The engine's write path is pipelined: MemTable flushes run on a background worker behind an atomic freeze-and-swap, WAL group commit lets concurrent strict-durability writers share one fsync, arena slabs are reclaimed through a reference-counted lease protocol, and Level-0 SSTables are compacted into Level 1 in the background. The final whitepaper matrix shows DataVo (LSM Relaxed) at \num{1215413.207} OPS on the single-thread scaling curve versus SQLite WAL normal at \num{318474.934} OPS, and \num{626690.498} OPS on an 80/20 YCSB mixed workload versus SQLite at \num{233778.627} OPS. Under strict physical durability, WAL group commit lifts DataVo (LSM Production) from \num{2478.648} OPS at one thread to \num{9110.373} OPS at 32 threads: the single-writer case remains correctly bounded by the device's fsync latency, but concurrency now amortizes rather than multiplies it. The paper is deliberately not a victory lap: the pipelined design pays a visible write-amplification tax --- \num{66.443} MB on disk after one million inserted records versus SQLite's \num{58.405} MB (LiteDB records \num{154.461} MB) --- and the paper reports that regression alongside the wins. The evidence supports a bounded claim: managed runtimes are not the limiting factor when memory layout, specialization, lock behavior, and durability protocols are engineered explicitly.
\end{abstract}

\section{Introduction}
Database engines written in managed languages are usually evaluated under a suspicion that does not apply equally to native engines: every allocation, virtual dispatch, object wrapper, dictionary lookup, and serializer is treated as a potential tax on the critical path. That suspicion is justified when the engine represents rows as object graphs and routes query execution through reflection or dynamic maps. In those designs, the engine performs more work than the query requires. It chases pointers through entity instances, allocates per-cell wrappers, boxes primitive values into \texttt{object}, and forces the garbage collector to later reconstruct order from allocation churn.

DataVo's benchmark results show a different managed-runtime operating point. The strongest DataVo results occur when the database stops behaving like a conventional object mapper and starts behaving like a storage system: rows are serialized into schema-ordered byte arrays, fixed-width primitives are patched in place when the predicate and schema make that safe, vector search avoids document-object materialization, and an LSM MemTable generation stores nodes inside an arena-backed skiplist rather than as one managed object per insert.

The central contribution of this paper is the framing and analysis of DataVo's Storage Virtualization Model (SVM). SVM is the architecture boundary that lets the SQL-facing engine preserve relational semantics while the physical layer sees byte arrays, row identifiers, typed cells, and backend-specific mutation contracts. The distinction matters because it explains both the wins and the losses. DataVo LSM can beat SQLite WAL normal in elapsed time when the benchmark measures engine throughput rather than raw device flush latency. DataVo's deep document path can beat LiteDB because relational decomposition avoids document graph reconstruction. DataVo's strict durability mode deliberately exposes the physical SSD synchronization boundary; when every logical update is forced through a synchronous durability barrier, the benchmark measures the storage device more than the database engine.

\section{The SVM Abstraction Layer}
\subsection{Why Conventional Managed Abstractions Stall}
Traditional managed database designs often model the tuple as a high-level object: an entity instance, a dictionary from column name to value, or a document tree. That approach is ergonomic but expensive. Each lookup becomes a hash-table or reflection operation. Each primitive can be boxed. Variable object sizes damage locality. Object headers, references, and runtime type metadata inflate the memory footprint. Even when the CPU has enough arithmetic capacity, pointer-chasing causes cache misses and turns row access into a latency-bound operation. This is the same pressure that led lakehouse engines such as Photon to bypass managed-runtime execution for hot vectorized paths when JVM garbage collection and object overhead became bottlenecks \cite{photon}.

The problem is amplified in write-heavy benchmarks. A dictionary-based update path must deserialize the row, construct a mutable representation, update one or two fields, validate constraints, serialize the row again, and then allocate the resulting payload. The system pays for a full-row object transition even when the logical operation is a primitive overwrite. Under concurrency, this combines with locks and write-ahead logging to increase tail latency.

\subsection{SVM: Logical Query Virtualization Over Byte Layout}
DataVo's SVM layer separates the logical query from the physical representation. The SQL engine still exposes databases, tables, primary keys, projections, predicates, and updates. Below that boundary, the storage engine accepts serialized row payloads and row identifiers through \texttt{IStorageEngine}. A row is not primarily an object; it is a schema-ordered byte layout. The schema defines the cell order, null flags, and primitive encodings. Query compilation can then resolve column ordinals once and treat the row as an indexed byte sequence. This design borrows the spirit of classical database architecture: recovery, versioning, and physical layout must be explicit rather than hidden behind language objects \cite{aries,mvcc}.

This is the same conceptual move native engines make with tuple descriptors and slot arrays. The difference is that DataVo performs it inside C\#. The managed runtime remains present, but the hot path uses spans, byte arrays, typed cells, and explicit fast-path eligibility checks. SVM therefore virtualizes the relational model without forcing the storage layer to materialize relational objects.

\subsection{SVM as a Byte-Addressed Storage Contract}
SVM is not a new storage theory; it is a managed implementation of classical slotted-page and byte-addressed storage contracts \cite{arch-dbms}, optimized specifically to bypass managed-runtime object graphs and pointer-chasing. The contract is byte-addressed in the conventional sense: schemas define ordinal cell positions, serializers define fixed encodings, and storage engines operate on row identifiers plus encoded payloads. What the name marks is the placement of that classical boundary inside a managed runtime, where the default idioms (entity objects, property bags, reflection-driven mapping) would otherwise erase it. Query compilation resolves names into ordinals once, then hands the hot path a stable byte layout. The storage layer never needs to reason about object graphs, reflection, or property bags. It only sees rows as addressable byte ranges. That boundary lets the engine choose between in-memory typed arrays, disk append logs, LSM generations, or vector indexes without changing the relational surface.

The reactive subsystem uses related ideas from incremental view maintenance: DBToaster's higher-order deltas \cite{dbtoaster}, factorized maintenance state \cite{fivm}, DBSP's compositional stream algebra \cite{dbsp}, and Shared Arrangements' reuse of indexed state \cite{shared-arrangements}. SVM supplies the physical substrate for that direction. Rows remain byte layouts, committed changes become compact deltas, and repeated object reconstruction is removed from the common path.

\subsection{Storage Contracts and Backend Substitution}
The interface contract is deliberately small. \texttt{IStorageEngine} appends serialized rows, inserts batches, reads by row id, scans rows, deletes rows, drops tables, drops databases, and compacts tables. \texttt{IStorageBackend} extends that contract with a backend identifier, enabling runtime selection among in-memory, disk, LSM, WASM, and custom providers. This black-box seam is useful because the query layer can target one contract while each backend optimizes layout and persistence.

The seam is also dangerous. A generalized interface returns \texttt{byte[]} and \texttt{IEnumerable} shapes, which can hide allocation from callers. Ref-struct iterators, borrowed buffers, and arena spans cannot cross ordinary interface boundaries without lifetime restrictions. DataVo partially resolves this with side-channel fast interfaces such as \texttt{IFixedWidthPatchStorageEngine} and typed-row storage paths. The trade-off is architectural complexity: the clean abstraction remains, but the highest-performance paths require explicit capability detection.

\section{Granular Engine Pipelines}
\subsection{Arena LSM Path: \texttt{StorageMode.Lsm}}
The LSM backend is the clearest expression of the low-allocation architecture, combining the log-structured write pattern of LSM systems \cite{lsm} with region-style lifetime control \cite{region-memory}. A \texttt{MemTable} generation is a single-writer sorted skiplist keyed by internal keys. Its nodes are not allocated as managed objects. Each node is one contiguous record carved from an \texttt{Arena}. The arena rents \texttt{byte[]} slabs from \texttt{ArrayPool<byte>.Shared}; allocation is a bump-pointer operation that advances an in-slab offset and returns a \texttt{Span<byte>} plus a stable handle. That handle packs the slab index into the high 32 bits and the in-slab offset into the low 32 bits, so skiplist forward pointers can be stored as arena handles instead of managed object references. The node layout is explicit: value length, key length, height, forward handles, internal-key bytes, and value bytes.

The generation lifecycle is pipelined. First, writes enter the active MemTable as versioned entries; the user key is the encoded row id and the internal key appends sequence information and a value type. Second, when the active MemTable crosses its size threshold it is frozen in place, a fresh active MemTable and a fresh WAL segment are swapped in atomically under the write gate, and the frozen generation is enqueued for a single background flush worker --- the crossing writer returns without performing any flush I/O, and writers block on the pipeline only when a bounded number of frozen generations are already queued (backpressure), never for a routine flush. Third, the background worker serializes the frozen generation through \texttt{SsTableWriter} into an immutable SSTable byte image, writes the file atomically, and registers it in the manifest as Level 0 metadata; only then is the generation's WAL segment deleted. Fourth, the frozen generation's arena slabs are returned to the shared pool in one disposal sweep --- deferred, if necessary, until the last read lease against that arena is released. This is the central arena behavior: allocation is cheap because it is monotonic within a generation, and reclamation is cheap because the entire generation has one lifetime, now bounded by its last reader rather than by the flush alone.

That design explains the \num{19.384} MB GC allocation profile in the current LSM disk CRUD row (Table~\ref{tab:disk}). Most short-lived per-write structures that would otherwise become managed heap objects are converted into slab-relative byte ranges and handles. The allocation profile is not zero, because row payloads, lists, manifest metadata, and benchmark harness structures still allocate, but it is low relative to the \num{867.471} MB the legacy object-per-write disk mode recorded on the same workload in the original exploratory matrix.

\subsection{SSTable Bloom Filters}
DataVo's Bloom filter is part of the current SSTable implementation, not merely a future optimization. \texttt{SsTableWriter} creates a filter with 10 bits per expected key, computes the probe count as \(\mathrm{round}(10\ln 2)\), inserts the user-key portion of every internal key, serializes the filter as a dedicated filter block, and records that block in the SSTable footer. \texttt{SsTableReader} loads the filter before serving point lookups. If \texttt{MightContain} returns false, the lookup exits without scanning the data block. If the key may be present, the reader then checks key bounds and scans the single v1 data block.

The implementation follows Bloom's one-sided-error membership model \cite{bloom}. False positives are allowed and only cost an unnecessary data-block probe; false negatives would be correctness bugs. For that reason, the reader validates every loaded SSTable by checking that the persisted filter answers positively for every data-block key. DataVo also uses Kirsch and Mitzenmacher's double-hashing result operationally: one 64-bit FNV-1a hash is split into two 32-bit values and the \(k\) probe positions are generated as \(g_i=h_1+i h_2\), avoiding \(k\) independent hash computations while preserving Bloom-filter behavior in practice \cite{less-hashing}. This matters for managed code because membership testing becomes a fixed, allocation-free loop over a byte bitset.

\subsection{Fixed-Width Patching}
The fixed-width patching subsystem addresses a narrower but important case: point updates over primitive columns. The row serializer stores cells in schema order, each preceded by a null flag. For eligible \texttt{INT}, \texttt{FLOAT}, \texttt{BIT}, and \texttt{GUID} columns, \texttt{RowSerializer.TryOverwriteFixedWidthCell} advances through the encoded row until it reaches the target ordinal and overwrites the primitive bytes directly. GUIDs are serialized as the same 16-byte little-endian sequence used by \texttt{Guid.TryWriteBytes}, preserving the internal high/low split used by \texttt{CellValue} and preventing string-format round trips.

The compiled update path is conservative. \texttt{TryUpdateFixedWidthFastPath} requires zero-allocation compiled updates to be enabled, storage mode to be Disk or LSM, change capture to be disabled, the predicate to target the single integer primary key, the primary-key fast lane to be present, assigned columns to be fixed-width, and secondary indexes or key constraints not to require maintenance. When those conditions hold, the engine avoids dictionary materialization and object serialization. In Disk mode the current implementation still performs an out-of-place row move: tombstone the old row, append patched bytes, update MVCC metadata, and repoint the primary-key index. In LSM mode it routes through \texttt{IFixedWidthPatchStorageEngine}, appending a new LSM version for the patched bytes. The resulting version chain is conceptually aligned with multiversion concurrency control, but DataVo's current implementation should not be read as a complete MVCC proof system \cite{mvcc}.

\subsection{The Black-Box Interface Seam}
The \texttt{IStorageEngine} seam is a productive compromise. It permits backend substitution, testing, and isolation of persistence details. It also forces engineering discipline: whenever the storage engine needs to expose a zero-allocation operation, the team must decide whether to generalize the interface or add a capability interface. The current system does both. The generic path remains byte-array based; the fast path discovers \texttt{IFixedWidthPatchStorageEngine}. This avoids contaminating every backend with LSM-specific details, but it also means fast-path coverage is incomplete by design.

\subsection{Hardware Drivers}
The benchmark behavior is driven by three hardware-level facts. First, Apple Silicon cores reward contiguous memory traversal and punish pointer-heavy object graphs with cache-miss latency. Second, fsync and \texttt{FlushToDisk} are orders of magnitude slower than memory writes; an out-of-place update strategy that forces synchronous persistence can dominate every other optimization. Third, vector search over 1,536-dimensional embeddings is bandwidth- and locality-sensitive. Flat arrays and pooled scratch buffers are competitive; document encodings that repeatedly allocate arrays and documents are catastrophic.

\subsection{Native Storage \& Open-Addressing Maps}
DataVo stores GUIDs as native 128-bit scalar cells rather than strings. The first 64 bits live in the numeric slot of \texttt{CellValue}; the second 64 bits are packed into the otherwise unused decimal bitset payload when the discriminator is \texttt{Guid}. This keeps the common row cell compact, preserves zero-allocation typed reads, and keeps GUID predicates in the same L1/L2-friendly cell array as integers, doubles, dates, and booleans.

The byte order is intentionally the same across \texttt{CellValue}, \texttt{RowSerializer}, and the compiled reader. \texttt{CellValue.From(Guid)} writes the GUID into a 16-byte span, reads the low and high halves as little-endian 64-bit values, and \texttt{AsGuid} reconstructs the identical 16-byte sequence. \texttt{RowSerializer} emits and reads the same 16 bytes, so persisted rows, typed rows, and source-generated readers agree on the physical representation.

The index layer adds an O(1) GUID fast lane alongside the integer fast lane. Integer primary-key lookups use \texttt{ConcurrentInt64Int64Map}, an open-addressing map backed by flat key, value, and state arrays with lock-free reads and internally serialized writers; it replaces per-entry dictionary nodes with contiguous slots, so bulk ingest stops paying one allocation per indexed key and the probe loop stays branch-light and cache-friendly. GUID primary-key lookups use a concurrent dictionary keyed by the native 128-bit \texttt{Guid} cell, whose comparer performs a hardware-gated equality check by loading both GUID byte sequences into \texttt{Vector128<byte>} registers. Secondary GUID indexes use key-to-row-id buckets. The result is a no-boxing, no-string, no-parse path from compiled query parameter to row id.

\subsection{Architectural Guarantee of Single-Row Visibility}
DataVo's point-read path holds no locks, so its correctness cannot be argued from mutual exclusion. It must instead be argued from what memory a concurrent reader is physically able to observe. This subsection gives that argument as an architectural proof: two mechanical invariants, enforced by construction in the storage layer, together make the classical failure mode of lock-free designs (the torn read, in which a reader observes some bytes of a row from before an update and other bytes from after it) not merely improbable but unrepresentable. The shape of the guarantee is snapshot isolation's read stability restricted to the single-row case \cite{si-critique}: a reader operates against a stable committed version that concurrent writers cannot perturb, and writers install new versions without waiting for readers to drain.

The first invariant is immutability of published row images. Every row version in the LSM path is a self-contained byte array produced by the row serializer, and once a reference to that array has been published to the latest-row version table, no code path writes through it again. The fixed-width patch pipeline makes this concrete. \texttt{TryPatchFixedWidthRow} first clones the current image, applies \texttt{TryOverwriteFixedWidthCell} to the private clone, appends the clone to the WAL and the active MemTable as a new LSM version, and only then publishes the clone's reference. Mutation happens off-path, on memory no reader can reach; publication happens only for memory that will never again be mutated. The consequence is unconditional: any row image a reader holds is frozen for as long as the reader holds it, regardless of how many updates commit concurrently.

The second invariant is atomic, ordered publication of version references. The latest-row version table (\texttt{LsmLatestRowStore}) maps a row id to exactly one object reference per slot, and installing a new version is a single store to that slot. The CLI memory model guarantees that aligned reads and writes of object references are atomic \cite{ecma335}, and on the 64-bit hardware this paper targets, Apple Silicon ARM64 as well as x86-64, an aligned 8-byte store is single-copy atomic at the cache-coherence level. There is consequently no interleaving in which a reader loads half of an old pointer and half of a new one. Pointer atomicity alone, however, is not sufficient on weakly ordered hardware: the processor must also be prevented from making the pointer visible before the row bytes it addresses. DataVo enforces this with release/acquire discipline. Versions are published with \texttt{Volatile.Write} and dereferenced behind \texttt{Volatile.Read}, so a reader that observes the new reference is guaranteed to observe the complete row image behind it. The integer primary-key fast lane obeys the same protocol: \texttt{ConcurrentInt64Int64Map} writes a slot's key and payload before publishing its occupancy state with a release store, and a published key is never rewritten in place. The guarantee is structure-agnostic; it held equally for the \texttt{ConcurrentDictionary}-based fast lanes that the flat maps replaced, because both designs reduce publication to one atomic reference-width store.

Together the two invariants close the proof by case analysis. Consider a reader racing an update to the same row. The reader performs exactly one acquire-load of the row's version reference, and that load is the linearization point of the read \cite{linearizability}. If the load executes before the writer's release-store, the reader obtains the pre-mutation image: complete, because it was published under the same protocol by an earlier writer, and stable, by the immutability invariant. If the load executes after, the reader obtains the post-mutation image: complete, because the release fence ordered every byte of the clone before the reference became visible. There is no third case. A hybrid row, some cells old and some cells new, would require either in-place mutation of a published buffer (excluded by the first invariant) or observation of a partially written reference (excluded by the second). The torn state has no address in the system. It cannot be read because it never exists in reachable memory.

Two properties of the managed runtime complete the argument for heap-owned row images. First, reclamation safety is inherited rather than engineered: a native lock-free design must deploy hazard pointers or epoch-based schemes to prevent a writer from freeing a version some reader still holds, whereas in DataVo the reader's acquired reference keeps the version reachable and the garbage collector cannot reclaim reachable memory. Second, collector compaction is invisible to the protocol: the runtime may relocate a row image, but it re-targets every reference as part of collection and never exposes an intermediate copy to managed code.

One honest boundary must be drawn around that inheritance, because it is exactly where a managed engine can quietly reintroduce native-style unsafety. Arena slabs are rented from \texttt{ArrayPool<byte>.Shared} and returned for reuse; a returned slab is not garbage-collected memory but recyclable memory, and a span still addressing it after return would be a logical use-after-free --- the reader would observe whatever unrelated workload rented the slab next. GC reachability does not protect against this, because the pool holds the array alive while its contents are overwritten. DataVo closes this gap with a reference-counted lease protocol on the arena: any reader of a generation's spans --- including the background flush worker serializing a frozen MemTable --- first acquires a lease, and a disposed generation defers its slab return until the last lease is released. The rule is the moral equivalent of epoch-based reclamation stated in one sentence: slabs rejoin the shared pool only after every read that began before the generation's retirement has completed. With that protocol in place, the earlier claim can be restated precisely: object lifetimes are protected by the collector, pooled-slab lifetimes are protected by leases, and neither surface exposes recycled memory to a live reader.

The scope of the claim is deliberately precise. For the point reads that dominate the benchmark matrix, the read set is a single row version, so the snapshot property degenerates to exactly what the invariants provide: the reader sees one committed version in its entirety, never a blend. Multi-row transactional reads layer MVCC visibility metadata over the same immutable version chain, in the lineage of multiversion concurrency control \cite{mvcc}; because versions are never mutated, a snapshot is defined purely by which versions are visible, never by a race on their contents. Consistent with the fixed-width patching discussion above, this is a visibility guarantee, not a serializability proof: write-write ordering is enforced by the writer path's per-table write lock. Stated strictly: this proof is limited to single-row visibility and the prevention of torn reads. Multi-row ACID transactions are coordinated above this layer by the engine's transactional lock manager and MVCC visibility metadata --- a logical transaction coordinator that is deliberately separate from the storage-level mechanism proven here --- and full multi-row serializability, phantom-read prevention, and distributed write-conflict resolution live in that layer, outside the scope of this storage-level proof.

\subsection{Measurement and Timing Protocol}
All timings use \texttt{System.Diagnostics.Stopwatch}: per-operation latencies are captured as monotonic \texttt{Stopwatch.GetTimestamp} tick deltas and converted through \texttt{Stopwatch.Frequency}, which maps to the platform's high-resolution counter (\texttt{mach\_absolute\_time} on macOS, \texttt{QueryPerformanceCounter} on Windows). Percentiles are computed over the full per-operation latency arrays, not sampled subsets.

Warm-up is provided by each scenario's preload phase rather than by discarding measured iterations: every engine first executes its full preload (for example \num{10000} baseline orders in the risk profiles and \num{100000} records in the YCSB and thread-scaling scenarios) through the same code paths the measured phase exercises, which JIT-compiles the hot methods and populates caches before the first timed operation. No measured iterations are discarded afterwards; the reported distributions include every timed operation, so first-operation effects that survive preload appear in the tails rather than being edited out.

Allocation figures bracket the measured window with \texttt{GC.GetTotalAllocatedBytes(precise: true)} after forced full collections (\texttt{GC.Collect}, \texttt{WaitForPendingFinalizers}, \texttt{GC.Collect}), and measure allocation volume, not resident memory. Each engine runs against a fresh working directory, and console progress output is redirected away from the timed window. Threads are not pinned: macOS exposes no public thread-affinity API, so the thread counts in the scaling scenarios are degrees of parallelism placed by the macOS scheduler across performance and efficiency cores. This is a source of run-to-run variance acknowledged in the threats-to-validity discussion.

\subsection{The macOS \texttt{fsync} Discrepancy and the I/O Boundary}
The final phase of the investigation changed the interpretation of the disk results. In the first strict-durability runs, DataVo (LSM Production) required approximately \num{205000} ms to process \num{50000} auto-commit point updates, while SQLite appeared to complete the same scale in roughly \num{4000} ms under \texttt{WAL,FULL}. At first glance, this suggested that the native C engine had a decisive persistence advantage. The hardware arithmetic contradicted that interpretation. A true device-level forced write on the tested NVMe SSD costs on the order of \num{4} ms. Multiplying that latency by \num{50000} independent auto-commit updates predicts approximately \num{200000} ms, which is precisely the wall DataVo reached.

The discrepancy is a durability-semantics problem, not a managed-runtime problem. DataVo's strict path uses \texttt{FileStream.Flush(true)} and directory synchronization in the publication path, forcing each auto-commit mutation through the operating-system durability boundary. On macOS, standard SQLite \texttt{PRAGMA synchronous=FULL} is not equivalent to enabling the platform-specific \mbox{\texttt{F\_FULLFSYNC}} path. SQLite exposes that stronger behavior through \texttt{PRAGMA fullfsync}; the SQLite documentation states that \texttt{fullfsync} controls use of \mbox{\texttt{F\_FULLFSYNC}} on systems that support it, and that only macOS supports that primitive \cite{sqlite-pragma}. Therefore, a default \texttt{WAL,FULL} run on macOS can complete after ordinary POSIX synchronization has reached the drive cache rather than after the strongest macOS full-device flush has been requested. The observed result was an apples-to-oranges durability comparison. The validation run with \texttt{PRAGMA fullfsync=1} changed SQLite's unbatched update time to \num{209282.571} ms, with \num{4.028958} ms P50 and \num{6.855750} ms P99, matching the predicted hardware synchronization wall.

The correction was methodological. A serious application would not execute \num{50000} independent auto-commit updates when it intends to mutate a batch. Both the bulk insert and bulk update phases were therefore wrapped in explicit transactions, amortizing the forced synchronization cost across the batch. That change moves the measurement away from the SSD queue limit and back toward the storage-engine question: how much work does the database perform per logical point operation once the unavoidable durability fence is paid once per transaction? Under that corrected methodology, DataVo (LSM Relaxed) reaches \num{247.080} ms and \num{17.782} MB in the disk CRUD WAL matrix, while SQLite WAL normal records \num{842.914} ms and \num{23.190} MB. DataVo (LSM Production) records \num{501.870} ms, demonstrating that the production durability path remains competitive when the benchmark measures transaction-level persistence rather than pathological auto-commit device flushing.

The thread-scaling benchmark preloads \num{100000} records and then executes \num{100000} random point reads plus \num{10000} point updates at fixed degrees of parallelism. The goal of this benchmark is not to declare one engine universally superior, but to quantify the concurrency ceiling of database-level locks versus lock-free MemTables within a managed runtime. The measured effect is a strict-durability curve that scales from \num{2478.648} OPS at one thread to \num{9110.373} OPS at 32 threads --- a 3.675541x improvement from concurrency alone. The single-thread number is unchanged by design: one writer has nobody to share an fsync with, and the device's synchronization latency is not negotiable. What group commit removes is the multiplication of that latency across threads.

\subsection{Background Flush, Compaction Debt, and Crash Recovery}
The previous revision of this paper documented two production liabilities in this section: an inline MemTable flush that stalled every concurrent writer for the duration of the SSTable serialization and its fsyncs, and unbounded Level-0 accumulation with no background compaction. Both are now engineered out, and the replacement mechanics deserve the same explicit statement the liabilities received.

The write stall is resolved by a pipelined MemTable lifecycle. When the active MemTable crosses its \num{32} MB threshold, the crossing writer freezes it, atomically swaps in a fresh MemTable and a fresh WAL segment under the write gate, enqueues the frozen generation, and returns --- the SSTable serialization, file and directory fsyncs, and manifest edit all execute on a dedicated background worker. Writers block on the pipeline only when two frozen generations are already queued, which is backpressure in the deliberate sense: the writer waits because the device genuinely cannot absorb the ingest rate, not because routine maintenance borrowed its thread. The measured effect is direct: DataVo (LSM Production) YCSB write P99 fell from \num{268.069416} ms (inline flush absorbed into the strict tail) to \num{50.721583} ms, and production throughput on the same workload rose 3.3x. The residual \num{50.721583} ms tail is the group-commit fsync convoy under a 20-percent-write mix, not a flush stall.

Compaction debt is now bounded by a background worker as well. Every flush appends a Level-0 SSTable; when the manifest's live Level-0 count reaches four files, the flush worker merges them into Level~1 on the same maintenance gate that serializes flush I/O, so compaction never races a flush or an explicit maintenance command. Point-read latency does not depend on Level-0 count in this design (reads resolve through the authoritative latest-row table), so the compaction policy's job is space reclamation and cold-open cost, not read performance. The space-and-recovery table prices what remains honestly: at measurement time the pipelined design carries retained WAL segments and transient level overlap worth about 14 percent of footprint against SQLite. A leveled policy beyond L0-to-L1 is the remaining compaction work.

Crash recovery follows a fixed sequence with no interactive repair, now generalized to WAL segments. On open, the engine reads the manifest; because SSTables and the manifest are published with write-to-temporary, fsync, atomic-rename, and directory-fsync steps, a crash yields either the old or the new manifest state, never a mixture. Live SSTables are enumerated newest-first and the latest-row table is rebuilt from their entries. Then every surviving WAL segment is replayed in generation order --- a generation's segment is deleted only after its SSTable and manifest edit are durable, so the set of surviving segments is exactly the set of generations whose data lives nowhere else. Within each segment, every frame is validated by length, header, and CRC32C checksum; replay consumes the longest valid prefix and the first torn or corrupt frame truncates the tail, so a partially written frame from the moment of the crash is discarded rather than misinterpreted. Sequence-number and row-id watermarks are restored from the recovered state, and replay is idempotent under sequence numbers, so a crash during recovery itself re-replays harmlessly. In strict-fsync mode every acknowledged write is in the durable prefix by the group-commit contract --- the acknowledgment does not return before a covering fsync completes; in relaxed mode the OS-buffered suffix of the WAL can be lost with the power event, but the recovered prefix is always internally consistent.

\section{Threats to Validity}
The benchmark log is a single run family on Apple Silicon macOS, not a statistically powered cross-platform study. It does not cover Linux servers, x86 NUMA effects, different SSD firmware, cold caches, very large databases, or multi-process writers. GC allocation is not resident memory, and the SQLite/sqlite-vec managed allocation numbers include the benchmark harness boundary rather than SQLite's internal native allocator. The macOS durability discussion depends on the distinction between ordinary POSIX synchronization and the platform-specific \mbox{\texttt{F\_FULLFSYNC}} path; the added \texttt{PRAGMA fullfsync=1} validation run supports the hardware-durability interpretation, but additional devices and operating systems should still be measured before generalizing the exact latency constant. The document, vector, and YCSB-style workloads are shape-dependent. These caveats reduce the scope of the claims but do not invalidate the measured facts.

First, \texttt{datavo\_benchmark\_figures.py} is a standalone Matplotlib script that parses the canonical rerun log (\path{whitepaper_benchmark_rerun_2026-07-03-v2.txt}), writes an auditable coordinate file (\path{whitepaper_figure_calculations.txt}) recording every plotted value and derived ratio with its source, and renders the PNG, PDF, and SVG assets from that file. \section{Conclusion}
The DataVo benchmark matrix supports a disciplined conclusion. Managed C\# can reach, and in several scalar workloads exceed, native-class embedded database performance when the hot path avoids object-oriented storage abstractions and uses SVM byte contracts, schema-ordered byte layouts, arena-backed LSM generations, fixed-width compiled update paths, native GUID cells, and carefully placed concurrency barriers. The final thread-scaling curve shows DataVo (LSM Relaxed) at \num{1215413.207} single-thread OPS versus SQLite WAL normal at \num{318474.934}, and --- the result this revision adds --- DataVo (LSM Production) scaling from \num{2478.648} to \num{9110.373} OPS across 1 to 32 threads under strict physical durability, because WAL group commit amortizes the device fsync across concurrent writers instead of multiplying it. The YCSB mixed workload shows DataVo at \num{626690.498} OPS with \num{0.000917} ms read P99 and \num{1.333833} ms write P99, while SQLite reaches \num{233778.627} OPS with \num{0.010500} ms read P99 and \num{3.408333} ms write P99. The space benchmark is the honest counterweight: DataVo's pipelined design measures \num{66.443} MB after one million records against SQLite's \num{58.405} MB (LiteDB records \num{154.461} MB), the visible write-amplification cost of retained WAL segments and level overlap.

The strongest architectural lesson is not that every flush should be avoided. It is that benchmarks must separate device physics from engine design. When DataVo was asked to perform \num{50000} strict auto-commit updates, it correctly hit the approximately \num{200000} ms physical synchronization wall. SQLite's apparently faster \texttt{WAL,FULL} result on macOS was not equivalent unless \texttt{F\_FULLFSYNC} was enabled. Once transaction boundaries were aligned, the comparison returned to the database engine itself: write layout, lock behavior, allocation topology, and recovery protocol.

A fair question from an enterprise architect is why this engine should exist in .NET at all when native LSM implementations such as RocksDB are mature and freely embeddable. The answer this paper's measurements support is operational rather than ideological. Embedding a native engine in a C\# estate means shipping and patching platform-specific native binaries, crossing a foreign-function boundary on every operation, and marshalling keys and values across that boundary --- costs that are per-call, permanent, and invisible to managed profilers. It also splits the diagnostic story: a latency spike must be chased across two allocators, two threading models, and two toolchains. DataVo keeps the entire storage stack inside the managed runtime: the same \texttt{dotnet-trace}, EventPipe, and allocation-profiling tools that observe the application observe the engine; the memory-safety guarantees that hold for application code hold for the storage code; and deployment is one self-contained, ahead-of-time-compilable artifact. The benchmark matrix shows the performance price of that choice is not what managed-runtime folklore predicts --- on these workloads there is a performance dividend --- so the trade resolves to native-tier storage behavior without the native operational surface.

DataVo is therefore no longer merely an experimental fast path. The production-hardening work added WAL integration, atomic SSTable and manifest publication, directory synchronization, ARM64 memory-ordering barriers, MVCC snapshot-retention safety, and now the pipelined write path: background MemTable flushes behind an atomic freeze-and-swap, WAL group commit for strict durability, lease-guarded arena reclamation, and background Level-0 compaction. The remaining frontier is narrower and more concrete: extend the compaction policy beyond the Level-0 trigger into a leveled hierarchy that reclaims the measured footprint overhead, expand cross-platform durability measurements, and repeat the matrix on Linux and x86 hardware. The central result is already clear: managed runtimes are not the limiting factor when the database engine is architected as a storage system rather than an object graph manager.
